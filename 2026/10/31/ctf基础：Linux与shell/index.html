学习笔记：WSL 环境、Linux 与 Shell 基础

一、操作环境与路径

1.1 Windows、WSL 与远程主机

  • Windows：电脑的宿主系统。
  • WSL：Windows 中运行的 Linux 环境。
  • 远程机器：通过 SSH 等方式连接的另一台机器。

**命令在哪里执行，通常就操作哪里的文件和进程。**在 WSL 中运行 curl -o，文件保存在 WSL 能访问的指定路径；SSH 登录后执行 mkdir，目录创建在远程机器上。

1.2 当前目录与路径

pwd       # 查看当前目录
ls        # 查看目录内容
cd 目录   # 切换目录
路径写法 含义
. 当前目录
.. 上一级目录
~ 当前用户主目录
work/greeting.json 相对于当前目录的路径
/home/Lambda/env-practice 从 Linux 根目录出发的绝对路径 
cd ~/env-practice
cat work/greeting.json

**路径不是命令。**进入上一级目录用 cd ..，不是单独输入 ..。当前目录决定相对路径的起点。

二、项目目录与 Python 环境

2.1 项目结构

env-practice/
├── .venv/          Python 虚拟环境
├── original/       原始文件
├── work/           工作副本和练习数据
├── scripts/        程序、脚本
├── results/        输出结果
├── notes.md        学习和操作记录
└── requirements.txt

习惯：**保留原件，在副本上操作，把结果单独保存。**部分文件是教学要求，不能仅凭目录示意认为已全部创建。

2.2 虚拟环境

在项目目录中激活、检查、退出：

source .venv/bin/activate
command -v python
python --version
deactivate
  • 激活主要调整当前终端环境，让虚拟环境的命令优先被找到。
  • 激活不改变当前目录，也不替换系统 Python。
  • 切换目录不会自动退出虚拟环境；新终端通常需要单独激活。
  • 不激活，也能直接指定解释器：
~/env-practice/.venv/bin/python scripts/greet.py

已观察到的环境版本为 Python 3.14.4；激活后解释器路径为 /home/Lambda/env-practice/.venv/bin/python。

2.3 依赖管理

python -m pip list
python -m pip freeze > requirements.txt
python -m pip install -r requirements.txt
  • pip list 查看当前 Python 环境的包，不是当前目录的文件。
  • requirements.txt 是依赖清单，不是包本身，也不是完整项目。
  • json 等标准库通常不需要额外安装，不列入普通依赖清单。
  • apt 安装 Linux 工具，不会把它们装进 .venv。

2.4 程序与配置分离

  • .py 是程序代码；.json 是数据格式，不是编程语言。
  • JSON 的键和值要区分，字符串使用英文双引号。
{"name": "Lambda"}

示例程序 scripts/greet.py：

import json


with open("work/greeting.json", encoding="utf-8") as file:
    config = json.load(file)


print("你好，" + config["name"] + "！")

在项目目录运行：

python scripts/greet.py > results/greeting-output.txt
cat results/greeting-output.txt

代码读取 config["name"] 时，可以改变值；把键改成 username 而不修改代码，可能产生 KeyError。缺少配置文件可能产生 FileNotFoundError。

三、常用文件操作

命令 用途
ls -la 显示隐藏项及详细信息
ls -lh 用便于阅读的单位显示大小
mkdir -p 路径 创建目录及所需父目录
cp -i 源文件 目标 复制，覆盖前询问
mv -i 源文件 目标 移动或重命名，覆盖前询问
cat 文件 输出文件内容
diff 文件1 文件2 比较内容，不修改文件

移动文件不会改变 Shell 当前目录。diff 无输出且退出码为 0，表示文件内容相同。

3.1 含空格路径的处理

mv -i "my notes.txt" "study notes.txt"

这是两个路径参数。目标不存在时，此例是重命名。

cat "$HOME/env-practice/work/space practice/study notes.txt"

双引号中的 $HOME 会展开；引号中的 ~ 不会进行主目录展开。

3.2 less：分页查看文件

less notes.md
按键 功能
空格 / b 下一屏 / 上一屏
/文字，回车 向下搜索
n / N 下一个 / 上一个匹配
q 退出

在 less 中搜索文字，不是在执行 Shell 命令。

四、文件查找与内容搜索

4.1 find：按条件查找文件

find work/linux-review -type f -name 'app.log'
find work -type f -name '*.json'
  • 搜索起点写在条件前面。
  • -type f：普通文件。
  • -name：按名称匹配，区分大小写。
  • -iname：按名称匹配，不区分大小写。
  • 通配模式加引号，避免由 Shell 提前展开。
  • 本次 WSL 使用的 find 省略起点时通常默认搜索当前目录，但明确写起点更清楚。

4.2 grep：搜索文件内容

推荐顺序：

grep 选项 '搜索文字' 搜索路径
grep -rn 'ERROR' work/linux-review
选项 含义
-r 递归搜索
-n 显示行号
-i 忽略大小写
-F 固定文字匹配，而非正则表达式

输出通常是：

文件路径:行号:匹配到的整行内容

find work -type f | grep 'json'

这里右边筛选的是路径字符串，不是搜索这些文件内部的文字。管道传什么，右边就处理什么，不会自动打开路径指向的文件。

4.3 隐藏文件

  • 名字以 . 开头，通常被视为隐藏项；ls -a 可以显示。
  • 隐藏不等于加密，也不改变权限。
  • Bash 默认的 * 通常不匹配隐藏名称。
  • find 和 grep -r 不会默认因为目录隐藏就跳过它。

五、输入、输出、管道与重定向

编号 名称 用途
0 标准输入 接收输入
1 标准输出 输出正常结果
2 标准错误 输出诊断、报错信息
符号 功能
--- ---
> 或 1> 标准输出覆盖写入文件
>> 标准输出追加到文件末尾
2> 标准错误覆盖写入文件
< 从文件读取标准输入
| 左边标准输出交给右边标准输入

分别保存结果和报错：

cat work/greeting.json work/not-exist-demo.txt > results/content.txt 2> results/errors.txt

重要提醒：

  • 终端没有报错文字，不代表命令成功。
  • 2> 只改变报错去向，不会把失败变成功。
  • >> 不自动去重，重复执行可能产生重复行。
  • 不要将同一文件同时作为读取对象和 > 的输出目标，否则可能先被清空。

六、文件与目录权限

权限 普通文件 目录
r 读取内容 列出成员名字
w 修改内容 配合 x，增删、重命名目录项
x 允许尝试执行 进入目录、按名字访问成员 
ls -ld work

-d 查看目录本身。例如 drwxr-xr-x 依次表示类型、所有者权限、所属组权限、其他用户权限。

chmod u+x scripts/permission-demo.sh
chmod u-x scripts/permission-demo.sh
  • u 是所有者，+x 增加执行权限，-x 移除执行权限。
  • 目录只有 r、没有 x，不能仅凭 r 进入。
  • 读取文件需要文件自身的读取权限，也需要沿途目录的访问权限。
  • 文件只读，不代表一定不能删除；删除主要取决于所在目录权限，还可能受粘滞位、只读文件系统等限制。

直接执行与交给解释器读取不同：

./scripts/permission-demo.sh
bash scripts/permission-demo.sh

后者通常不要求脚本自身具有执行权限，但仍需读取和路径访问等权限。加执行权限不会让不兼容的文件格式自动变成可运行程序。

七、文件类型识别与归档压缩

7.1 file：识别文件类型

file /bin/bash
file work/greeting.json

**改后缀不会改变文件格式。**JSON 改成 .jpg 不会变成图片，tar 改成 .tar.gz 不会自动压缩。

/bin/bash 输出中的常见字段：

字段 含义
ELF Linux 常见二进制格式
64-bit 64 位格式，不是 64 字节
LSB 小端字节序
pie executable 位置无关可执行程序
x86-64 处理器架构
version 1 (SYSV) ELF 格式与 ABI 标识，不是 Bash 版本
dynamically linked 运行时需要加载共享库
interpreter /lib64/ld-linux-x86-64.so.2 指定动态加载器
BuildID 构建标识，不是安全认证
for GNU/Linux 3.2.0 文件记录的内核兼容性信息，不是当前内核版本
stripped 部分调试符号已移除，不代表损坏

7.2 打包与压缩

  • 打包：把文件、目录结构等放进一个归档。
  • 压缩：利用重复与规律，用更少的数据表示内容。
  • 压缩可利用重复次数、重复片段引用、为常见符号分配短编码等方法。
  • gzip 通常使用 DEFLATE，结合重复片段引用和霍夫曼编码。
  • ZIP、gzip 是无损压缩，正常解压可逐字节还原内容。
格式 特点
.tar 通常只打包
.gz gzip 压缩数据流
.tar.gz 先 tar 打包，再 gzip 压缩
.zip 支持多文件归档与压缩，也允许直接存储

已经压缩过的数据通常不容易继续明显压小；小文件压缩后也可能更大。Windows 可以通过 7-Zip 等工具处理这些格式，较新 Windows 11 的内置支持取决于系统版本和更新。

7.3 tar 常用命令

# 创建；同名包可能被覆盖
tar -cvf results/config-demo.tar work/greeting.json


查看列表
tar -tf results/config-demo.tar


创建 gzip 压缩的 tar 包
tar -czvf results/config-gzip-demo.tar.gz work/greeting.json


查看压缩包列表
tar -tzf results/config-gzip-demo.tar.gz


解压到提前创建的专用目录
mkdir -p work/unpack-gzip-demo
tar -xzvf results/config-gzip-demo.tar.gz -C work/unpack-gzip-demo

-c 创建，-t 查看，-x 解包，-z 使用 gzip，-v 显示处理过程，-f 指定归档文件，-C 指定解包位置。解包可能覆盖已有同路径文件，应使用专用目录。

7.4 ZIP 常用命令

zip results/config-zip-demo.zip work/greeting.json
unzip -l results/config-zip-demo.zip
unzip -t results/config-zip-demo.zip
输出或选项 含义
adding 添加文件
stored 0% 直接存储，没有压缩节省，不是失败
Length 成员未压缩时的大小，单位为字节
Date、Time 包内记录的成员修改时间
-l 查看列表
-t 测试完整性
OK 对应成员测试通过

截图验证：包内有一个 work/greeting.json，未压缩大小为 22 字节，完整性测试通过。22 字节不是整个 ZIP 包的大小。

mkdir -p work/unpack-zip-demo
unzip -n results/config-zip-demo.zip -d work/unpack-zip-demo
  • -n：不覆盖已有同名文件。
  • -d：指定解压目录。
  • 包内路径会保留，最终位置可能为 work/unpack-zip-demo/work/greeting.json。
  • zip 遇到已有同名包通常更新对应成员，不等同于清空归档重新创建。

**完整性测试通过，不代表内容安全，也不代表 JSON 配置正确。**不要把来源不明的归档直接解压到重要目录或随意执行其中的程序。

八、HTTP、curl、SSH 与 nc

8.1 启动本地 HTTP 服务

cd ~/env-practice
python3 -m http.server 8000 --bind 127.0.0.1 --directory results

浏览器访问 http://localhost:8000/。

  • 127.0.0.1：回环地址。
  • 8000：端口。
  • --directory results：指定服务目录，按启动时当前目录解析。
  • 网站根路径 / 对应该服务目录，不是 Linux 根目录。

避免相对路径出错：

python3 -m http.server 8000 --bind 127.0.0.1 --directory "$HOME/env-practice/results"
现象 含义
200 请求成功
404 已收到 HTTP 响应，但资源未找到
连接被拒绝等连接失败 没有成功建立相应连接

favicon.ico 是浏览器可能自动请求的网站图标，其缺失通常不影响其他文件访问。服务访问日志只记录到达自身的请求，不会监控浏览器全部活动。

8.2 curl：发送 HTTP 请求

curl http://127.0.0.1:8000/greeting-output.txt
curl -i http://127.0.0.1:8000/greeting-output.txt
curl -f -o work/downloaded-greeting.txt http://127.0.0.1:8000/greeting-output.txt
  • -i：包含响应头。
  • -o：指定运行 curl 这一端的保存位置，已有文件可能被覆盖。
  • -f：让 HTTP 错误状态通常按失败处理，避免把错误正文作为正常下载保存。
  • 保存成功不等于内容符合预期；仍需检查。

8.3 SSH 与 nc

工具 主要用途
curl 理解 HTTP 等协议并请求资源
ssh 加密、认证后进行远程操作
nc 通用网络连接、收发数据

SSH 格式示意，不是直接照抄执行的地址：

ssh 用户名@服务器地址
ssh -p 端口号 用户名@服务器地址
  • 不能用 ssh http://127.0.0.1:8000 访问网页。
  • 把 SSH 指向 HTTP 端口，也不会让协议自动兼容。
  • nc 连通端口不等于获得远程 Shell；它通常不内置加密和登录认证。
  • 首次 SSH 连接应通过可信渠道核对主机指纹。
  • 输入登录密码不显示字符或星号是正常现象。
  • exit 通常用于退出远程 Shell。

**端口连通后，还需要使用对端理解的协议。**连接 HTTP 服务后输入 ls，不会自动执行远程命令。

九、进程、信号与退出码

9.1 前台与后台进程

  • 程序文件：磁盘上的文件。
  • 进程：程序正在运行的一次实例。
  • PID：进程编号。

**前台服务运行期间，Shell 通常在等待，不会把输入文字当作新命令执行。**先确认出现 Shell 提示符，再输入命令。

9.2 退出码与条件执行

echo "$?"

查看上一条命令的退出码，需紧接着检查。

  • 0：通常成功。
  • 非 0：失败或命令约定的特殊结果。
  • grep 的 0 表示找到匹配，1 表示无匹配，2 表示错误。
连接符 含义
&& 左边成功才执行右边
|| 左边失败才执行右边
; 不根据左边成功与否判断，按顺序继续 
cd ~/env-practice && pwd
cat work/greeting.json || echo '读取失败'

十、进程与运行位置

  • 程序是代码和相关数据；进程是程序运行的一次实例。
  • 同一个程序可以产生多个进程。
  • PID 是进程编号，不能当作永远不变的身份。
  • Shell 的任务编号（例如 %1）与 PID 不是同一种编号。
  • 前台进程占用当前终端的交互位置，Shell 通常等待它结束。
  • 后台运行不等于脱离终端，也不保证关闭终端后仍继续运行。

常见命令用于回顾，不表示本次全部执行过：

ps
pgrep -af 'python3 -m http.server'
jobs

运行前台 HTTP 服务时输入其他文字，不代表 Shell 执行了这些命令。应另开终端，或先停止前台服务并等到 Shell 提示符出现。

十一、退出码与条件执行

11.1 退出码

Shell 中通常约定：

  • 0 表示命令报告成功。
  • 非零表示其他状态，含义由具体程序定义，不一定都表示同一种错误。
  • 命令成功不代表业务内容一定正确。
某条命令
printf '退出码：%s\n' "$?"

$? 是最近完成命令的退出状态，应紧跟目标命令检查。执行了其他命令后，它可能已被覆盖。

例如 diff 的退出状态可区分内容相同、内容不同和执行出错；不能把所有非零一律解释成同一种失败。

11.2 条件执行

命令A && 命令B
命令A || 命令B
命令A ; 命令B
  • &&：A 退出为0时，才执行 B。
  • ||：A 退出非0时，才执行 B。
  • ;：不根据 A 的退出码选择是否执行 B。

A && B || C 不是所有场景都等价于完整的 if/else：若 B 失败，也可能继续执行 C。

十二、信号

信号是进程接收异步通知的一种机制，不是网络报文，也不等同于退出码。

信号 常见含义与边界
SIGINT 中断；Ctrl+C 通常向前台进程组发送此信号
SIGTERM 请求终止；kill 默认发送，程序可处理、忽略或按默认方式终止
SIGKILL 强制终止，不能被捕获、忽略或阻塞，不给正常清理机会
SIGSEGV 常见于无效内存访问引发的故障；具体含义需结合上下文 
kill 实际PID

以上只是格式示意，不可照抄“实际PID”。执行前应确认目标，不能停止不认识的进程。

  • kill 名称不代表默认强杀，默认信号是 SIGTERM。
  • 发出信号不等于目标已经退出，应另行确认。
  • 不应把 SIGKILL 当作第一步常规操作。

十三、段错误与判断依据

  • 段错误通常与无效内存访问及系统保护机制有关。
  • 越界访问不一定立即导致段错误。
  • 程序没有崩溃，不证明没有越界或其他内存问题。
  • 出现段错误，不自动证明漏洞可以利用。
  • 还需要结合具体代码、输入、运行环境与诊断信息分析。

在 Bash 中，因信号终止的状态常表示为：

128+信号编号

在常见 Linux 环境中，SIGSEGV 编号为11，因此常见状态为139。

**仅凭139不能独立证明根因。**程序也可主动返回某个退出码，Shell 和运行环境的报告方式也应核对。

本次没有故意制造段错误，不将未做的实验记为完成。

十四、标准输入、输出与错误输出

文件描述符是进程用于引用已打开输入输出资源的编号。资源不只包括普通磁盘文件，也可能是终端、管道或套接字。

编号 常用名称 方向
0 标准输入 程序读取
1 标准输出 程序输出正常结果
2 标准错误 程序输出诊断或错误信息

这些编号属于进程的资源引用，不是文件扩展名，也不是系统内永久固定的文件身份。

14.1 管道

命令A | 命令B

普通管道默认连接 A 的标准输出与 B 的标准输入，不自动包含 A 的标准错误。

管道传递字节，不会自动打开字节内容中写出的文件路径。

14.2 常见重定向

写法 含义
> 文件 标准输出写入文件，通常创建或截断
>> 文件 标准输出追加到文件
2> 文件 标准错误写入文件
< 文件 从文件取得标准输入
2>&1 将描述符2连接到描述符1当时指向的目标

重定向由 Shell 处理；覆盖文件前必须确认路径，尤其注意变量为空的情况。

十五、重定向顺序与作用

Shell 按从左到右的顺序处理此处的重定向。

15.1 先重定向标准输出，再合并错误输出

命令 > both.txt 2>&1
  1. 描述符1先连接到文件。
  2. 描述符2再复制描述符1当时的连接。
  3. 正常输出和错误输出都进入文件。

15.2 先复制标准输出，再重定向标准输出

命令 2>&1 > only-out.txt
  1. 描述符2先连接到描述符1原先的目标，通常为终端。
  2. 描述符1随后改接文件。
  3. 描述符2不会随着描述符1后来的改变而自动改变。

2>&1 复制的是当时的连接，不是让2永远跟随1。
