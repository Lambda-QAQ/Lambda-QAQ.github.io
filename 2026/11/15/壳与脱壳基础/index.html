壳与脱壳基础

1. 壳的定义与用途

壳是在原程序外增加的一层启动、还原或保护逻辑。

以压缩／加密壳为例：

执行壳代码 → 解压／解密原程序内容 → 转交执行权 → 原程序运行
  • 压缩壳：如 UPX，运行时解压程序内容。
  • 加密壳：运行时解密受保护的代码。
  • 复合保护：可能组合加密、反调试、完整性检查。
  • 虚拟化保护：将部分代码转换为自定义虚拟指令，由解释器执行。

这些保护方式可以组合使用。脱壳的目标是便于分析原程序，不是解题终点。

2. 识别加壳的线索

结合多项证据，不能凭单一现象下结论。

现象 判断边界
字符串少 可能有壳，也可能只是字符串加密或本来就少
没有 main 也可能只是去除了符号
F5 失败、栈分析报错 不等于有壳或文件损坏
UPX 标记、查壳工具结果 是线索，可能被修改或误识别
运行时还原代码，再转去执行 是值得重点追踪的解包特征

辅助工具：file、strings、Detect It Easy、IDA Pro。

UPX 不识别，不代表文件没壳；它不是通用查壳工具。

3. 标准 UPX 文件的处理

file challenge          # 确认格式、架构
upx -l challenge        # 查看 UPX 压缩信息
upx -t challenge        # 检查压缩数据完整性

保留原件，使用尚不存在的副本名：

cp challenge challenge.unpacked
upx -d challenge.unpacked

然后将解压结果重新导入 IDA Pro、新建数据库，继续分析输入与校验。

注意：

  • -t 通过不等于程序逻辑已验证。
  • 解压失败先读报错、检查格式及支持情况，不盲目加 --force。
  • Windows PE 与 Linux ELF 的手工处理步骤不能照搬。

4. 识别校验逻辑

建立这条证据链：

用户输入 → 检查／变换 → 比较结果 → 接受／拒绝

需要回答：

  • 数据是否来自输入？
  • 它约束输入的什么条件？
  • 条件不满足会怎样？

只找到 Correct、cmp、main，都不足以证明已恢复完整校验。长度、内容及其他前置条件可能分散在不同函数中。

5. 输入数据流

从输入落点开始：

输入方式 重点追踪
命令行参数 argv[1]
scanf("%s", buf) buf
fgets(buf, size, stdin) buf
read(fd, buf, size) buf 与实际读取长度

遇到以下操作，要继续接上链条：

别名：p = input              → 追 p 的使用
复制：memcpy(tmp, input, n)  → 继续追 tmp
调用：check(input, n)        → 对应函数形参
返回：result = check(...)   → 看 result 如何控制分支

IDA 中可按 N 重命名变量，但变量高亮不会自动追踪所有副本和别名。

动态验证时：先预测一个字节的变化，再在关键比较处检查实际值，避免无目标单步。

6. 磁盘映像与运行时映像

加壳后的磁盘文件通常同时包含启动代码和压缩或加密的数据。启动代码先恢复部分内容，再把执行交给恢复后的程序逻辑。因此，磁盘上的字符串、导入项与反汇编结果可能只能反映启动代码。

7. 区分恢复逻辑与业务逻辑

连续读取、变换和写入大块数据的循环可能承担内容恢复。业务逻辑则往往围绕输入、状态与输出组织。单凭循环或跳转无法判断其用途，需要结合数据来源、写入位置和后续调用关系。

8. 压缩、加密与混淆的区别

压缩主要改变存储体积，加密需要经过解密才能恢复内容，混淆主要增加理解代码和数据的难度。一个壳可以组合几种方式。运行时还原只说明程序得到了执行所需的内容，不能由此推断所有内容会同时出现在内存里。

9. 静态线索如何相互印证

线索 其他可能原因
可读字符串很少 文件体积小、符号已剥离
原始字节分布接近均匀 压缩资源、媒体数据或加密数据
导入项很少 静态链接、程序功能简单
入口附近是短代码 启动桩、运行库初始化

分析时应结合文件结构、入口行为和数据去向，给结论保留相应的证据边界。

10. 为什么内存映像和原文件会不同

装载时，系统可能按段映射文件、补齐零初始化区域并处理重定位。运行过程中，程序也可能创建新的内存区域或恢复数据。文件偏移、映像中的虚拟地址和进程里的实际地址属于不同坐标。观察内存中出现的内容时，应同时记录它的来源和所属区域。
